MDZ vs OKF 2026: Two New Markdown Formats Tested

Markdown spent twenty years as a render-me-now syntax. In November 2026 it is becoming something more: a package you can ship, and a corpus your AI agents can actually read. Two new specs - MDZip's .mdz and the Open Knowledge Format - define that future from opposite directions. Here is what each one actually is, what problem it solves, and where a Markdown-to-rich-text converter still fits.

Two announcements landed in the same week this November, and they sound almost identical if you only read the headlines. MDZip Studio shipped for macOS on November 10, 2026, bringing a desktop app for a file format called .mdz. Days earlier, the Open Knowledge Format (OKF) - a spec from two Google Cloud tech leads for organizing Markdown so AI agents can consume it - crossed its second public revision.

Both describe themselves with the same words: "portable," "Markdown-native," "for humans and AI agents." But they are not competitors. They operate on different layers of the stack, solve different failures, and - this is the part almost no coverage has stated clearly - they compose. An OKF knowledge bundle can be zipped into an .mdz and emailed. An .mdz can be extracted into an OKF bundle for an agent to index. The right question is not "which format wins" but "which failure mode are you trying to fix."

The problem both formats are attacking

Markdown has a well-known portability gap: the text travels everywhere, but the context does not. A Markdown file that references images/cover.png and depends on a companion AGENTS.md for instructions is not a self-contained artifact. Send just the .md file and the recipient gets text with broken references. Zip the whole folder and the recipient gets an unstructured archive they have to interpret manually. Neither is a good handoff to a colleague, a publisher, or an AI agent that needs to know which file is the entry point.

The 2026 twist is the agent. When the consumer of your Markdown is a language model doing knowledge work - summarizing your docs, answering questions against your playbook, drafting from your style guide - the failure modes multiply. Agents do not guess well. Give an agent a bare folder of 40 Markdown files with no index and no type metadata, and it will either hallucinate structure or burn tokens reading everything. OKF's documentation states the premise plainly: agents don't guess at structure, they read it. Both specs are, in different ways, attempts to make Markdown legible to machines without making it illegible to humans.

MDZip .mdz: Markdown as a shippable package

The .mdz format - spec version 1.2.1, status Final, dated October 25, 2026 - is deliberately unglamorous. The specification's own summary reads: "It's a ZIP file." An .mdz is a standard ZIP archive with a .mdz extension and the proposed MIME type application/vnd.mdzip. Files inside are stored or DEFLATE-compressed, never encrypted. Rename it to .zip and any archive manager on earth opens it.

What the extension adds is a thin layer of agreed-upon structure:

  • Entry-point discovery. The manifest's entryPoint field declares which document opens first; failing that, index.md; failing that, the only Markdown file at the root. If it is still ambiguous, conforming apps must ask rather than guess.
  • Two modes. The default document mode holds one main document. A project mode keeps several documents as a browsable set and requires a manifest declaring so.
  • A manifest.json. Optional for hand-made archives, but every MDZip tool writes one with at least spec.version and entryPoint.
  • Human and agent notes. Optional README.md and AGENTS.md at the root explain the archive to whoever - or whatever - opens it without MDZip tools.
  • Safety rules. Apps must not run scripts from an .mdz while displaying it, or extract files outside the destination folder.

The ecosystem has moved fast. The spec lists conformant core libraries across five languages - Kotlin/Java (Android), Swift (iOS), pure Lua, and two others passing the same shared conformance tests - plus MDZip Studio 1.7.0 for Windows, macOS, and Linux (Homebrew included, with Finder double-click handling on Mac), a VS Code extension, an Obsidian plugin, and a Google Voice exporter. An .mdz file you create on a Linux desktop can be opened by an iOS library and validated by a Lua script, and every one of them interprets the same entry point.

The spec is also explicit about what .mdz is not. It is not a replacement for EPUB - the FAQ makes the contrast directly: EPUB is a ZIP-based container whose content is XHTML, built for publication and reading systems. .mdz is the same single-file packaging idea but Markdown-native, authoring-oriented, and far lighter in structure. If EPUB is for books, .mdz is for the document you are still editing.

Example: a single-document .mdz as the spec describes it:

document.mdz (ZIP archive)
├── index.md          # Recommended entry point
├── manifest.json     # Written by every MDZip tool
├── README.md         # Optional: human usage notes
├── AGENTS.md         # Optional: guidance for AI agents
├── images/
│   └── cover.png
└── styles/
    └── document.css

OKF: Markdown as a machine-legible knowledge corpus

The Open Knowledge Format approaches the same portability gap from the other side. Where .mdz packages a document for transit, OKF organizes a living corpus for use. Its own description is austere: a directory of Markdown files, YAML frontmatter, three rules. That's the entire format.

The three rules, from the spec:

  1. Every .md file (except the reserved index.md and log.md) needs parseable YAML frontmatter.
  2. Every frontmatter block needs a non-empty type field (concept, howto, reference, decision, metric), so agents route each file to the right handler without heuristics.
  3. The reserved files index.md and log.md follow a defined structure - the index lists what the bundle contains, the log tracks changes.

Everything else is deliberately unstandardized. The spec's authors - Sam McVeety and Amir Hormati, Tech Leads in Data Analytics Engineering at Google Cloud, who announced OKF on June 12, 2026 - made a bet that knowledge-management standards die by over-specification. OKF "nails down the structural conventions needed for a knowledge corpus to be self-describing, and stops there."

The current version, v0.2 (published July 24, 2026), adds the feature that makes OKF genuinely agent-ready: trust signals. Frontmatter fields named sources, generated, verified, status, and stale_after let an agent distinguish a curated, human-verified page from one that was machine-generated and never checked. In a world where agents increasingly write the docs they also read, provenance is not a nice-to-have - it is the difference between a corpus you can trust and one you cannot.

A minimal OKF bundle looks like this:

my-knowledge-bundle/
├── index.md
├── what-is-okf.md
└── validation-rules.md

---
type: concept
title: What is OKF
sources: https://example.com/spec
verified: 2026-11-01
status: current
---
# What is OKF

The Open Knowledge Format is a spec for representing
knowledge as markdown files.

The spec's FAQ connects OKF to a pattern that keeps reappearing under different names - what Andrej Karpathy called the "LLM Wiki" in a widely-circulated gist: LLMs don't get bored, don't forget to update a cross-reference, and can touch 15 files in one pass. The bookkeeping that causes humans to abandon personal wikis is exactly what LLMs are good at. OKF is the first attempt to standardize that pattern: an Obsidian-style vault, but with the structure an agent needs to navigate it deterministically.

Read the table as a routing guide, not a scorecard. Shipping a finished whitepaper to a client who uses different tools? That is .mdz. Standing up a knowledge base that your team's agents query daily? That is OKF. Both? Zip the OKF bundle into an .mdz - the spec explicitly supports multi-document project archives with index.md as a landing page, which is exactly what an OKF index.md already is.

Where Markdown-to-rich-text conversion still fits

Both specs stop at the same boundary: they get your Markdown organized and portable, but neither one pastes a formatted post into LinkedIn. That last mile - from structured Markdown to the rich-text clipboard format that LinkedIn, X Articles, Notion, Medium, and Substack accept on paste - is still a conversion problem, and it is still solved by a different kind of tool.

The workflow composes cleanly:

  1. Author in Markdown, with whatever structure your project needs - a plain file, an OKF-typed bundle, or an .mdz archive.
  2. Extract the document you want to publish. From .mdz: open the archive and copy the entry-point .md. From OKF: pick the concept or howto file whose frontmatter type matches your intent.

  4. Paste into the platform and publish. Bold, headings, lists, links, and code blocks survive intact.

The verdict

MDZ and OKF are the two halves of a trend that will define Markdown's next decade: the format is growing up from a render-me-now syntax into infrastructure. .mdz answers "how do I ship a Markdown document without it falling apart in transit." OKF answers "how do I keep a Markdown corpus that an AI agent can actually use." Neither answer is complete without the last mile - converting your structured Markdown into the rich text that publishing platforms accept - and that last mile is where a privacy-first, client-side converter earns its place in the pipeline.

FAQ

What is the difference between MDZ and OKF?

MDZ (.mdz) is a file format: a ZIP archive with a .mdz extension that packages one or more Markdown documents with their images, styles, and a manifest.json into a single portable file. OKF (Open Knowledge Format) is a directory convention: a folder of Markdown files with YAML frontmatter and three structural rules, designed so AI agents can navigate a knowledge bundle without bespoke tooling. In short, .mdz is a package you send; OKF is a folder you keep. They solve different problems and can be used together.

Is an .mdz file just a ZIP file?

Yes, by design. An .mdz is a standard ZIP archive with a .mdz extension and the proposed MIME type application/vnd.mdzip. You can rename it to .zip and open it in any archive manager. The .mdz extension signals intent: this is a Markdown document package, not a generic archive. MDZip adds a thin layer of agreed structure on top of ZIP: an entry-point convention (index.md by default), an optional manifest.json with metadata, and safety rules for tools that open it.

Who created OKF and where does it come from?

OKF was designed by Sam McVeety and Amir Hormati, Tech Leads in Data Analytics Engineering at Google Cloud, and announced via the Google Cloud Blog on June 12, 2026. It is published under an open license, with the canonical repository at GoogleCloudPlatform/open-knowledge-format. The current version is v0.2, published July 24, 2026, which adds trust signals (sources, generated, verified, status, stale_after) for provenance tracking. The format is vendor-neutral: no Google Cloud dependency is required to use it.

Do I need special software to open .mdz files?

No. Because .mdz is a ZIP archive, any archive manager can extract it, and the Markdown inside is plain UTF-8 text that any editor can read. Purpose-built tools - MDZip Studio (now on macOS as of November 10, 2026), VS Code extensions, Obsidian integration, and core libraries for Android, iOS, and Lua - add conveniences like entry-point discovery and manifest parsing, but they are optional, not required.
