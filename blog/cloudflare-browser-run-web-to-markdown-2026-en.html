Cloudflare Browser Run 2026: Web to Markdown in One Call

Cloudflare's Browser Run /snapshot endpoint can now return Markdown, PDF, links, scraped elements and AI-extracted JSON from a single page load. We read the changelog, the endpoint docs and the pricing page, then checked the whole pipeline against md2rich's own converter — including the parts that do not work the way the UI implies.

On November 19, 2026, Cloudflare shipped a quiet but genuinely useful update to its /snapshot endpoint. Before it, a workflow that wanted a page's Markdown and a PDF of that same page had to ask twice — two page loads, two sets of rate limits, and a real chance the page had changed between the two requests. Now a single request returns HTML, screenshots, Markdown, the accessibility tree, PDFs, links, scraped elements and AI-extracted JSON, all captured from one page load.

For anyone whose job involves pulling a web page apart and turning it into something publishable, that is a small change with a large effect. It is also the kind of change that is easy to over-hype, so this article is mostly about the limits: what the endpoint actually guarantees, what it charges, and where it genuinely does not help.

We read the changelog entry, the endpoint documentation and the pricing page, and we checked md2rich's own conversion pipeline against the same problem. What follows is what we found.

What actually shipped

The four new formats are pdf, links, scrape and json. Each one reuses the options of the standalone endpoint it replaces, so you are not learning a second API:

Format Result field Required options
contentresult.content—
screenshotresult.screenshot—
markdownresult.markdown—
accessibilityTreeresult.accessibilityTree—
pdf newresult.pdf—
links newresult.links—
scrape newresult.scrapeelements
json newresult.jsonprompt or response_format

Two details in that table decide whether a request succeeds at all. The scrape format is unusable without an elements array of CSS selectors, and the json format is unusable without a prompt or a response_format. Omit either and the request does not degrade gracefully — it fails.

One naming note, because it will trip you up when you go looking for the docs: Cloudflare's browser products now live under Browser Run in the documentation, and the REST path reflects that. The endpoint is /accounts/<accountId>/browser-run/snapshot even though older tutorials and blog posts call the product "Browser Rendering".

The real win: one load instead of two

Here is the workflow this endpoint was built for, in the shape you would actually write it. Grab the page as Markdown, pull its links so you can cite sources, and produce a PDF so the draft has a printable reference — all from the same load.

curl -X POST 'https://api.cloudflare.com/client/v4/accounts/<accountId>/browser-run/snapshot' \
  -H 'Authorization: Bearer *** \
  -H 'Content-Type: application/json' \
  -d '{
    "url": "https://example.com/article",
    "formats": ["markdown", "links", "pdf"],
    "pdfOptions": { "format": "a4" }
  }'

The response carries three result fields — markdown, links and a base64 pdf — plus a meta block with the HTTP status and page title. The PDF is printed last on purpose, because print handlers can change the page.

Now compare that with the old way, where /markdown and /pdf were two separate calls. Two calls means two browser sessions, two page loads, twice the browser minutes, and — this is the part that actually bites — two chances to get different content. On a page with rotating banners, a live vote count or a "related articles" block, the PDF and the Markdown would not match. One load makes that class of bug disappear.

From captured page to published draft

Capturing is only half the job. The Markdown you get back still has to survive contact with a social platform's editor, and that is where the formats disagree with each other in ways that are not obvious until you paste.

A typical capture of a documentation page or a long-form article produces Markdown like this:

# Why writers are moving back to plain text

Long-form posts still lose their structure when pasted
into a social editor. The headings collapse, lists flatten,
and code blocks lose their monospace formatting.

- Headings above `h3` are stripped by most editors
- Tables rarely survive a paste
- Images are the first thing to disappear

The fix is not a better editor. It is a conversion step
that knows what the target editor will accept.

Example one — publishing to Medium. Medium's editor accepts a rich paste and re-uploads images itself, so the Medium mode in md2rich keeps <h1> through <h6>, lists, blockquotes, code and images, and strips tables (which Medium does not support natively). The clipboard receives an HTML fragment plus a plain-text fallback, and pasting it into the Medium editor keeps the heading hierarchy intact.

Example two — publishing to X Articles. X Articles is stricter. Its mode allows h2, h3 and h4 but strips h1 — the document title becomes the X Articles title field instead — and it drops tables entirely. Images are supposed to become [Image] placeholders.

That last one deserves a correction, because it is the sort of detail that quietly breaks a workflow. In md2rich's current implementation, the X Articles image placeholder does not appear. The tag whitelist removes <img> elements before the placeholder substitution runs, so an image reference is dropped from the output entirely rather than being replaced with a marker. If you publish screenshots to X Articles, upload them separately and leave the Markdown image syntax out of the draft. We are reporting the behaviour as implemented, not the behaviour the UI note implies.

One more accuracy note on LinkedIn: md2rich's LinkedIn mode deliberately returns plain text, not rich HTML, with a Markdown-hint header prepended. That is not a limitation being hidden — it is a design decision, because LinkedIn's composer does not accept rich HTML paste reliably and silently flattens it. The hint line the tool prepends is currently written in Chinese, so if you publish from an English-language account you will want to delete that line before posting.

What it costs

Cloudflare bills Browser Run by browser time, and Quick Actions — which is what /snapshot is — are charged for browser hours only, with no concurrent-browser surcharge.

  • Workers Free: 10 browser minutes per day.
  • Workers Paid: 10 browser hours per month, then $0.09 per additional hour.
  • JSON format: consumes Workers AI usage on top of the browser time.

Ten minutes a day on the free plan is genuinely enough for a personal publishing workflow — a few dozen article captures a day will not touch it. It is not enough for a crawler, and it is not enough for anything that fans out across many pages. Every Quick Actions response also returns an X-Browser-Ms-Used header reporting the browser time that request actually consumed, so you can meter your own usage per call rather than guessing.

The json format is the one to watch, because it bills twice: browser hours plus a Workers AI model invocation. For a page you only want the prose from, /markdown plus a second /scrape call is often cheaper than asking for AI-extracted JSON. Reserve json for when you genuinely need structured fields out of prose.

The limits that will surprise you

Four constraints are documented but easy to miss:

1. You must request at least two distinct formats. This is the rule most likely to waste an afternoon. Asking for only ["markdown"] is not a cheaper single-format request — it is an error. If you want one format, use that format's standalone endpoint.

2. Failure is all-or-nothing. If any requested format fails, the whole request fails. There is no partial response where the Markdown comes back and the PDF times out. On a page with one broken element selector, that means re-running the entire capture.

3. Capture order is fixed, and pages move. Formats are captured in a fixed order rather than the order you list them in, and a live page can change between captures. If you need the PDF and the Markdown to describe the same instant of a page, that is a real limitation of the design, not a bug in your request.

4. Browser Run is always identifiable as a bot. You can set a custom userAgent, but the documentation is explicit that this does not bypass bot protection, because the User-Agent string is configurable and therefore untrustworthy as a signal. Sites that want to block Browser Run should use its non-configurable request headers.

One practical tip for JavaScript-heavy pages: the default load behaviour can return an empty or half-rendered result because the browser considers the page loaded before the client-side rendering finishes. Setting gotoOptions.waitUntil to networkidle0 fixes it, at the cost of waiting for network activity to settle.

Where md2rich fits

Cloudflare's endpoint solves the inbound problem: getting a live web page into structured text. md2rich solves the outbound problem: getting your finished Markdown into a platform's editor with its formatting intact. They are complements, not competitors, and the seam between them is one copy-paste.

There is also a privacy difference worth being explicit about, because it decides which tool you reach for on a sensitive draft. Browser Run is a server-side product: the page is fetched, rendered and converted on Cloudflare's infrastructure, which means your source URL travels to Cloudflare and the rendered content exists on their side of the wire. md2rich is 100% client-side — the Markdown never leaves your browser, there is no backend, no upload and no tracking, and you can confirm it in the DevTools Network tab. If you are converting a draft you wrote, or a page you need to keep private, that distinction matters. If you are archiving public pages at volume, Cloudflare's endpoint is the better tool and the privacy question does not arise.

FAQ

Do I need /snapshot if I only want Markdown?

No. /snapshot requires at least two distinct formats. If Markdown is the only thing you want, use the standalone /markdown endpoint, which is a single-format call and returns the Markdown string directly. /snapshot only earns its place when you need two or more representations of the same page from a single load.

Is Cloudflare Browser Run free?

Partly. On the Workers Free plan you get 10 browser minutes per day. On Workers Paid you get 10 browser hours per month, then $0.09 per additional hour. The json format is separate from browser hours: it runs a Workers AI model and consumes your Workers AI usage on top of the browser time.

What happens when one format fails?

The whole request fails. Formats are captured in a fixed order rather than the order you list them in, a live page can change between captures, and any format that fails fails the whole request. For a JSON snapshot, a single actionTimeout budget (60 seconds by default, 120 maximum) covers navigation, captures, retries and the AI request together.

Can I set a user agent to get past bot protection?

No. The userAgent parameter does not bypass bot protection. Requests from Browser Run are always identified as a bot, and because the User-Agent string is configurable, destination servers that want to detect or block Browser Run should use its non-configurable request headers instead of the User-Agent string.

Where does md2rich fit in this pipeline?

Browser Run gets the page in; md2rich sends your draft out. Cloudflare's endpoint turns a live URL into Markdown plus optional PDF, links and structured data. md2rich then converts your Markdown into clipboard-ready rich text for the platform you are publishing to. The two cover opposite ends of the same job.

The verdict

The /snapshot update is a real efficiency win for one specific shape of work: capturing a live page once and needing several representations of it. If you need Markdown and a PDF, or Markdown and a set of scraped elements, you now pay for one page load instead of two, and you get a consistent snapshot instead of two slightly different ones.

It is not a general-purpose Markdown converter, and it is not free at scale. The two-format minimum, the all-or-nothing failure mode and the fixed capture order are real constraints, and the JSON format quietly bills twice. If you want one format, use the single-format endpoint — that is what it is for.

And once you have the Markdown in your editor, the last mile is the one that decides whether the post looks professional or like a broken paste. That step is what md2rich is for.
