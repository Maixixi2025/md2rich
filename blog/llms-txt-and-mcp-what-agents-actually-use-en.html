llms.txt and MCP Barely Helped: What Agents Use

One practitioner shipped an llms.txt and an MCP server, measured both, and watched neither change anything. The useful part is not that llms.txt and MCP are useless — it is the mechanism, and the eight things that did work.

In October 2026, Cristian Tabacitu published a post with a deliberately unsatisfying title: “llms.txt and MCP didn’t move the needle for us. Here’s what did.” He maintains Backpack for Laravel, a Laravel admin panel package with a decade of GitHub history. His team had done all the things that “make your package AI-ready” advice tells you to do. They shipped an llms.txt. They built an MCP server so agents could query their documentation. Then they measured what actually changed.

The result was: “Two of the things everyone tells you to add, llms.txt and an MCP server, barely helped us at all.”

This is one practitioner’s report, not a controlled study. But it is a careful one, it is reproducible (the package, the codebase and the docs are all public), and it landed on Hacker News with 31 points and 21 comments in which several people reported the same thing independently from unrelated projects.

It is also the correct correction to something we published on this site.

What md2rich got wrong in August

On August 3, 2026 we published Markdown for AI Agents 2026: llms.txt + AGENTS.md Guide on this blog. Its decisive claim was: “Cloudflare Agents Week 2026 just made the llms.txt + AGENTS.md pair essential.”

That was too strong, and this article is the correction. We had the direction right — AGENTS.md and in-project instruction files are the strongest part of the story — but we bundled llms.txt in with it and called the pair essential. Sixteen weeks of measurement from a practitioner who shipped both and watched neither move is worth more than our enthusiasm.

The rest of this article is what we should have written then: what actually happened, why it happened, and what to build instead.

What the measurement actually said

Tabacitu’s summary of the two failures is blunt:

llms.txt. “We shipped one. I don’t think it does much. Agents rarely go looking for it. When they do, they find a table of contents for docs they could already read.”

An MCP server. “We built one so agents could query our docs. The results were mixed at best. The agent has to decide to call it, and it usually doesn’t.”

And the generalisable lesson, which is the spine of this whole article:

“Anything the agent has to remember to go fetch is weak. What works is what’s already in front of it, or already in its head.”

Why llms.txt underperforms

Three reasons, and they compound rather than add.

It is a table of contents for something the agent can already reach. An llms.txt lists documentation URLs. If the agent has web access at all, it can find those URLs on its own; the file saves it a search, not a fetch. That is a token optimisation dressed up as a discovery mechanism.

Nothing standard points the agent at it. There is no rule anywhere that says a crawler or an agent must check for /llms.txt. The agent has to already know the convention exists. A convention you have to know about is not a discovery mechanism — it is a club for people who are already in the room.

When it does get read, it is a list, not content. Even in the best case the agent reads an index and then has to make a second decision about which entry to fetch. That is a second decision tax stacked on top of the first.

The Hacker News thread is direct about it: “It’s just a token saving mechanism… AFAIK Claude doesn’t look for this file, it needs to be explicitly instructed to.” And a newsletter operator in the same thread, who had put his own submission rules into his llms.txt, reported that he had “not seen a single one follow the rules in llms.txt yet.”

Why a docs-only MCP server underperforms

An MCP server is a tool. Tool use is a decision the model makes, weighed against every other tool in its context and against the cost of the call. When an agent already has general web retrieval available, adding a narrow documentation tool does not obviously win — it competes.

The specific failure Tabacitu describes is query quality: “the queries some of the AIs make are… laughable. Of course our MCP doesn’t return anything useful, your AI just typed two words.”

Tabacitu draws the dividing line himself, and it is the sentence that decides the whole question:

“An MCP server is a great fit for live data the agent can’t get any other way — or tool use. Static documentation isn’t that.”

That is the whole distinction. MCP is for live data and tool use. Static documentation is neither. If the docs are static, an MCP server is a worse front-end to them than plain HTTP, because it adds a decision gate in front of the same bytes.

Several people in the thread also noted that when they wanted documentation inside an agent, they reached for a general documentation index service rather than a vendor-run MCP server, and one put the diagnosis bluntly: “Absolutely no one should be using MCP for what should be a ripgrep across a corpus.”

The counter-case: token savings are real

Here is where the story gets more useful, because there is a measurable win in this area. It just is not discovery.

Cloudflare’s Markdown for Agents feature does real-time HTML-to-Markdown conversion at the edge when a request arrives with an Accept: text/markdown header. Cloudflare’s own blog post measured itself:

“This blog post you’re reading takes 16,180 tokens in HTML and 3,150 tokens when converted to markdown. That’s a 80% reduction in token usage.”

And Cloudflare reports that agents are already doing this on their own:

“We already see some of the most popular coding agents today – like Claude Code and OpenCode – send these accept headers with their requests for content.”

We verified this independently rather than taking the blog post’s word for it. Requesting Cloudflare’s own documentation page with an Accept: text/markdown header returns:

Content-Type: text/markdown; charset=utf-8
Vary: accept-encoding, accept
Content-Signal: ai-train=yes, search=yes, ai-input=yes
CF-Cache-Status: HIT

The body comes back as YAML frontmatter plus Markdown rather than HTML, with navigation, scripts and styles stripped and JSON-LD preserved as a fenced block at the end.

So Markdown for Agents is worth enabling — we covered the header and caching mechanics in Cloudflare Markdown for Agents: Headers & SEO 2026. But read carefully what it does: it makes an already-decided fetch cheaper. It does nothing whatsoever to make the agent decide to fetch you. An 80% token discount on a page nobody requested is worth zero.

That is the thesis of this article in one sentence: efficiency multipliers and discovery levers are different things, and only one of them was ever going to move the needle.

What actually worked

Here is Tabacitu’s list, and it is worth reading closely because almost none of it is AI-specific. A stable API is now training data: Backpack’s core API “has barely changed in the last four years”, and the side effect is that years of correct code sits in the model’s weights, so when an agent writes CRUD::column('name') it is “not searching or guessing. It already knows.” Open source means lots of examples, because ten years of issues, pull requests, tutorials and Stack Overflow answers are all training data and all searchable when an agent does go looking. Paid code shipped readable, with no obfuscation and no remote API, so an agent can read the actual source of a paid feature without being told to. Low ceremony, easy escape hatches: need a computed column is one line, small changes stay in one file, and that means less context for the agent to load and fewer places for it to get wrong. In-project agent instruction files, which was the biggest win. Generators the agent can run, because a command “gives the same correct result every time” while boilerplate the agent writes by hand is “a fresh chance to make a small mistake in every file.” Predictable naming, so agents guess right. And serving Markdown to agents, which he calls “a small win, and a free one if you’re already on Cloudflare.”

Eight items. llms.txt is not on the list, and a docs-only MCP server is explicitly argued against. We have covered the in-project instruction-file lever separately in Markdown Context Files: Cut AI Prompts to One Sentence, and the agent-readable-content question in Agent-Readable Markdown. This article is about the two things that did not work.

Laravel Boost, in numbers

The instruction-file lever deserves specifics, because it is the strongest positive result in the thread and it happens to be measurable.

Laravel’s official documentation describes Boost as providing “the essential guidelines and agent skills that help AI agents write high-quality Laravel applications.” The architectural detail that matters is that guidelines and skills load differently:

“Guidelines are loaded upfront when the AI agent starts, providing essential context about Laravel conventions and best practices that apply broadly across your codebase. Skills are activated on-demand when working on specific tasks, containing detailed patterns…”

Laravel reports a knowledge base of “over 17,000 pieces of Laravel-specific information.” Installation is two commands:

composer require laravel/boost --dev
php artisan boost:install

And boost:install “will generate the relevant agent guideline and skill files for the coding agents you selected during the installation process” — files that land inside the project and match the version actually installed.

This is a real counterweight to the idea that AI-specific additions never help. Boost is an AI-specific addition, and it is the single thing that worked best. The difference is precisely Tabacitu’s mechanism: it does not have to be fetched.

Translating this to a writing workflow

Tabacitu’s advice is aimed at package authors. If your job is publishing Markdown rather than shipping a library, the same levers translate fairly directly.

Stable APIStable canonical URLs and stable structure. Renaming or relocating a post breaks every external reference and every agent’s memory of it. Treat your URL as an API.
Open sourcePublish the source. A Markdown file on a public URL is greppable, indexable and readable by any agent with fetch access — no tool call required.
Readable paid codeReadable HTML. If your published page is a wall of scripts, an agent gets nothing. Server-rendered text gets everything.
Low ceremonyOne source file per post, not a build pipeline that emits twelve derived variants nobody maintains.

Serve MarkdownPublish the Markdown alongside the HTML — the one lever a content site can pull immediately and cheaply.

Our own audit, in public

We would rather apply the checklist to our own site than tell you to apply it to yours.

We ship an llms.txt. It is live at https://md2rich.com/llms.txt and returns 200 with about 1.5 KB of Markdown describing the tool. We are keeping it. It costs one file and an afternoon to maintain, and it is the polite thing to do for any agent that has been told to look. But we no longer describe it as a lever, and we would not spend an hour creating one if we did not already have it.

We do not currently serve Markdown to agents. We requested https://md2rich.com/ with an Accept: text/markdown header and got back Content-Type: text/html; charset=utf-8. The Markdown for Agents conversion is not enabled on our zone. We can enable it: it is free on Pro, Business and Enterprise plans, and it takes one toggle in the dashboard under Agent Readiness, or one API call to the content converter setting.

We are telling you that here rather than quietly switching it on, because by this article’s own logic the value is conditional: it makes our pages cheaper for agents that already found us, and does nothing for agents that did not.

We keep one canonical Markdown source per post and convert it client-side. That is the “stable API” lever applied to publishing: the Markdown file is the source of truth, and every rich-text output is a rendering of it rather than a separate document that has to be kept in sync.

The checklist

If you are responsible for how agents experience your content:

  1. Keep your Markdown source canonical and public. It is the thing agents can read without a tool call.
  2. Never move a published URL. Treat it as an API. It is the cheapest stability you can offer.
  3. Serve the Markdown, not just the HTML, if your host makes it a toggle. Verify with a real Accept: text/markdown request rather than trusting the dashboard.
  4. Put your house rules in a file the agent reads by default, not on a page it has to find.
  5. Do not build a docs MCP server for static content. If you need an MCP server, it should expose live data or an action.
  6. Keep an llms.txt if you have one, and stop counting it as a growth channel.
  7. Make your names guessable — same concept, same name, same order, every time.
  8. Reduce ceremony. If a change requires three files to customise, the agent has to load three files to make a small edit, and it will get something wrong.

FAQ

Should I delete my llms.txt?

No, and we are not telling you to delete ours. It is cheap, it is harmless, and there is a small chance an agent has been explicitly told to look for it. But stop treating it as a distribution channel or an SEO lever, and stop measuring it as one. Its maintenance cost is near zero and its measured effect on agent behaviour is near zero.

Are you saying MCP servers are useless?

No. We are saying a docs-only MCP server is a poor fit for static documentation. MCP is excellent for live data the agent cannot otherwise reach and for tool use: model routing, search APIs, write actions, account state. If your documentation is static, plain HTTP plus a Markdown representation is the better transport.

Then why does Laravel Boost work when a docs MCP server did not?

Because Boost is not fetched. php artisan boost:install writes guideline and skill files into the project, and the agent loads them at session start or when a matching skill activates. There is no decision to make and no token of query to get wrong. The mechanism is the whole difference.

Did Cloudflare Agents Week 2026 really make llms.txt essential?

No. That was our own framing in August 2026 and it was too strong. Agents Week made Markdown consumption a first-class concern, and Cloudflare shipped the edge conversion that makes serving Markdown cheap. But an agent has to already be looking for your content before any of that matters. We have corrected our position in this article rather than quietly changing it.

Is serving Markdown to agents worth it if it does not bring traffic?

Yes, on cost grounds rather than traffic grounds. Cloudflare measures its own blog post at 16,180 tokens as HTML and 3,150 tokens as Markdown — an 80% reduction — and reports that Claude Code and OpenCode already send the Accept: text/markdown header on their own. If you pay per token for agent traffic, that is a real saving. If you are hoping for citations, it is not a discovery mechanism.

If I keep one Markdown source, how do I publish it to LinkedIn and Medium?

That is the conversion half of the job, and it is the half md2rich does. The source stays as a Markdown file on your machine or your server; the rich text for each platform is generated from it. The source never changes, so the outputs never drift.

Bottom line

The strongest claim in Tabacitu’s post is not that llms.txt and MCP are useless. It is that they are weak levers: they work only if the agent has already decided to come, and they add a decision in front of content that did not need one.

What worked was not clever and not AI-specific. It was stable, readable, predictable, and already in the agent’s context. The AI-specific additions only helped when they put the right information in front of the agent without it having to ask.

There is a comfortable reading of all this for anyone publishing on the open web: the era of “make your site agent-friendly and traffic will follow” was mostly a list of things that felt like infrastructure. The lever that actually works is unglamorous. Publish the source. Keep the URL. Name things predictably. Leave the Markdown where a machine can find it.
