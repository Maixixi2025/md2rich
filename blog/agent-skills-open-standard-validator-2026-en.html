Agent Skills 2026: Inside the Open Standard for AI Agents

Anthropic handed Agent Skills to the Linux Foundation's Agentic AI Foundation, and the format is now an Apache-2.0 open standard maintained by named individuals across competing companies. We installed the reference validator and ran 22 deliberately broken skills through it, then ran md2rich's own converter against a test draft to see what those platforms really accept. Here is what the standard requires, what the validator catches, what it quietly lets through, and the one frontmatter mistake that gets your whole skill rejected.

On October 22, 2026, Anthropic donated Agent Skills - the open standard it has used to teach agents how to do specific jobs - to the Agentic AI Foundation under the Linux Foundation. Anthropic handed over the name and logo, the GitHub organization and the agentskills.io domain, and said engineers from Anthropic, Google and OpenAI would maintain the standard as individuals. Two lead maintainers were named: Mahesh Murag and David Soria Parra.

That is the headline, and it is the part every outlet wrote. But the interesting question for anyone building on this format is narrower: what does the standard actually require, and what does it let you get away with? The specification is short - the whole format is a folder with a SKILL.md file in it - and it ships with a reference validator called skills-ref. So we did something more useful than reading the rules: we cloned the specification repository, installed the reference library, and ran 22 test cases through the validator to find out which rules it enforces, which it only mentions in prose, and which it will happily let you get wrong.

Several of the results surprised us, and one of them is a rule that breaks a very natural instinct. We also ran md2rich's own conversion pipeline against the same drafts, because a skill that tells an agent how to publish to LinkedIn or X Articles is only worth writing if you know what those platforms actually accept.

What actually changed in October

The donation did not change the format. It changed who owns it. The specification repository is still agentskills/agentskills, still Apache-2.0 for code and specification files, still CC-BY-4.0 for documentation. What moved is the governance, and the governance document is dated November 4, 2026 - two weeks after the announcement - which tells you the paperwork was not ready on publication day.

The governance adopts a hierarchical structure borrowed from MCP and Python. Lead Maintainers hold final decision authority, Core Maintainers set the specification's direction, Maintainers own the documentation and the reference library, and Contributors handle issues and pull requests. The Lead and Core Maintainers together form a Technical Steering Committee. Membership belongs to the individual rather than the employer, no seats are reserved for particular companies, and Core Maintainers are explicitly required to be drawn from more than one organization.

On the AAIF side, Agent Skills appears on the Technical Committee's project list at Impact Stage, alongside nine other projects: Agent Router, Agent2Agent, agentgateway, AGENTS.MD, goose, Model Context Protocol, Open Responses, OpenEnv and OpenSandbox. The Technical Committee's own membership list names eight people, with David Soria Parra as chair and Caitlin McCaffrey of Microsoft as co-chair. The Foundation is real, the project is real, and the standard is still free to use without joining anything.

For a sense of scale, the specification repository carries about 27,400 stars and 2,046 forks, with 127 open issues, and the reference library it ships is published on PyPI as skills-ref, currently at version 0.1.1, requiring Python 3.11 or newer.

The rules, and the ones the validator actually checks

A skill is a directory. At minimum it contains a file named exactly SKILL.md holding YAML frontmatter followed by Markdown instructions. Optional siblings are scripts/, references/ and assets/, plus anything else you want to ship.

The frontmatter has exactly two required fields and four optional ones. Here is a complete, valid example - this one passes the reference validator:

---
name: md2rich-publish
description: Convert a Markdown draft into clipboard-ready rich text for
  LinkedIn, X Articles, Medium, Notion and Substack. Use when publishing or
  reformatting Markdown to a rich-text platform, when a pasted post loses its
  headings or lists, or when the user mentions Markdown-to-rich-text, rich
  paste, X Articles formatting or LinkedIn formatting.
license: Apache-2.0
metadata:
  author: md2rich
  version: "1.0"
---

# Publishing Markdown as rich text

## Steps

1. Read the draft.
2. Pick the target platform.
3. Convert the Markdown to that platform's allowed HTML.
4. Put the result on the clipboard as `text/html`, with a `text/plain`
   fallback in the same ClipboardItem.
5. Tell the user to press Cmd+V in the target editor.

The field rules, straight from the specification:

  • name (required): 1-64 characters, lowercase letters, digits and hyphens only. Cannot start or end with a hyphen. Cannot contain consecutive hyphens. Must match the parent directory name.
  • description (required): 1-1024 characters. Should describe both what the skill does and when to use it, and should carry the keywords an agent matches against.
  • license (optional): a licence name or a reference to a bundled licence file.
  • compatibility (optional): max 500 characters. Environment requirements - required packages, network access, intended product.
  • metadata (optional): an arbitrary map of string keys to string values for anything the spec does not define.
  • allowed-tools (optional): space-separated pre-approved tools. Marked experimental, and support varies between clients.

The most important design idea is progressive disclosure, and it is the reason the format is cheap enough to have 46 clients. Agents load skills in three tiers. At session start they read only the name and description of every available skill, roughly 50 to 100 tokens each. When a task matches a description, the full SKILL.md body loads, with under 5,000 tokens recommended. Scripts, references and assets load only when the instructions reference them. An agent with twenty skills installed does not pay for twenty instruction sets upfront.

What the validator enforces, tested against 22 cases

The specification ships its own reference library, so there is no need to take the rules on faith. Clone the repository, install the library, and you have a real gate:

git clone https://github.com/agentskills/agentskills.git
cd agentskills

uv venv --python 3.11 .venv
uv pip install --python .venv/bin/python ./skills-ref

.venv/bin/skills-ref validate ./my-skill
# Valid skill: my-skill

We then built 22 skills that each break exactly one rule, ran them all through that validator, and recorded what came back. Ten were accepted and twelve were rejected. The results:

  • Rejected: a top-level version field, an uppercase name, a leading hyphen, a trailing hyphen, consecutive hyphens, a directory name that does not match the skill name, a missing description, a 65-character name, a 1,025-character description, a 501-character compatibility string, a file with no frontmatter at all, and a duplicate description key.
  • Accepted: a 64-character name, a 1,024-character description, a 500-character compatibility string, a lowercase skill.md filename, an entirely empty body, and a 601-line body.

The version trap

Here is the finding that will bite the most people. The specification's own frontmatter example puts a version field inside metadata, which reads like it is the sanctioned way to version a skill. But the validator maintains a closed list of permitted top-level fields, and version is not on it. Put it at the top level and the skill is rejected outright:

# REJECTED
---
name: skill-a
description: A description of what this skill does and when to use it.
version: "1.0"
---

# Unexpected fields in frontmatter: version. Only
# ['allowed-tools', 'compatibility', 'description', 'license',
#  'metadata', 'name'] are allowed.


# ACCEPTED
---
name: skill-b
description: A description of what this skill does and when to use it.
metadata:
  author: example-org
  version: "1.0"
---

The rule is not obvious and the failure is total: the whole skill is refused because of one unexpected key. The fix is one line - move version inside metadata. If you write skills by hand, this is worth knowing before you write your first one.

Where the validator is lenient

The same run surfaced the other side of the coin. Several rules the specification states in prose are not enforced by the tool, which matters if you plan to trust skills-ref validate as your only gate.

  • An empty body passes. A SKILL.md with valid frontmatter and no instructions at all validates cleanly. The validator checks the metadata; it does not check that the skill teaches anything.
  • The 500-line guidance is not enforced. The specification says to keep your main SKILL.md under 500 lines. We built a 601-line skill and it validated without complaint. The same goes for the "under 5,000 tokens" guidance.
  • Non-ASCII names pass. A skill named with Chinese characters validates, because the implementation accepts any alphanumeric character rather than only a-z and 0-9 as the prose says. The directory name must match, and the match is a Unicode-normalised comparison.
  • Metadata values are coerced to strings. Write version: 1.0 inside metadata and it comes back as the string "1.0". A number 42 comes back as "42", a boolean as "true", and a nested mapping as a Python dict rendered as text.

The library also ships two other commands that are worth knowing about: skills-ref read-properties, which prints a skill's metadata as JSON, and skills-ref to-prompt, which generates the <available_skills> XML block for an agent's system prompt. That second one is how a client tells the model which skills exist and where to find them.

One more caveat about the library itself: its README says it "is intended for demonstration purposes only" and "is not meant to be used in production". The project is also not accepting code contributions to the reference library yet - bug reports and discussion are welcome, patches are not. Treat it as a teaching tool, which is exactly what it is.

Why this matters for a Markdown writer

Here is where the format earns its keep for this site specifically. If you draft in Markdown and publish to LinkedIn, X Articles, Medium, Notion or Substack, the hard part is not the Markdown - it is that every one of those platforms accepts a different subset of HTML, and the differences are not documented in one place.

That is exactly the kind of procedural knowledge a skill is for. A folder of plain Markdown instructions that says "for X Articles keep h2 through h4 and drop h1; for Medium strip the table family; for LinkedIn do not attempt a rich paste at all" is version-controlled, diffable, and reviewable. It stops the agent from re-deriving the rules on every draft.

The same draft pasted into Medium keeps the h1 and loses the table the same way. Pasting into a generic rich-text target keeps everything, table included.

Two behaviours here are worth encoding in a skill, because both surprise people. First, tables are silently destroyed on Medium and X Articles: the markup is stripped but the cell text survives as unformatted words, which reads like a rendering glitch rather than a conversion rule. A skill should tell the agent to rewrite a table as a bullet list before converting, not after. Second, LinkedIn is a special case entirely: md2rich does not attempt rich HTML paste for it at all, because LinkedIn's composer does not reliably accept it. The output is plain text that keeps the Markdown syntax visible, with a note that a browser extension is needed to render it.

The gap the standard has not closed

The honest caveat, and the thing to weigh before you install skills from strangers: the specification contains no security guidance. We checked the whole format documentation and the skill-creation guides - the words "malicious", "supply chain" and "prompt injection" do not appear in any of them, and "security" appears only in the governance document, where it describes how to route a security report and requires a spec proposal to state its security implications.

That is a reporting path, not a review process. There is no signature, no permission manifest enforced by the format, no manifest of what a skill's scripts will touch. A skill can bundle arbitrary scripts, and the agent that loads it may run them with whatever permissions your client grants.

Anthropic's own roadmap proposal, mentioned in the donation announcement, includes "security guidance for people who write and install skills" - so this is a known gap with a known owner. Until it lands, the practical rule is the old one: read the scripts before you install the folder, and treat a skill the way you would treat a Makefile you found on the internet. The format's own contribution guide is refreshingly candid about the culture around it: it requires that any AI assistance used in a pull request be disclosed, down to trivial spacing and typo fixes being the only exception.

The verdict

Agent Skills has become the closest thing 2026 has to a shared packaging format for agent instructions, and the move to the Linux Foundation is a genuine maturation: an Apache-2.0 specification, a neutral home, a governance model where membership belongs to the person rather than the employer, and a technical committee with an explicit "high bar for additions" philosophy that reads like it was written by someone who has watched specifications get bloated.

The format is also small enough to learn in an afternoon, which is the point. A folder, a SKILL.md, and a description good enough that an agent knows when to reach for it. Everything else is a convention the spec recommends rather than enforces.

For a Markdown writer, the practical version is simple. If you publish the same way to several platforms, the platform rules are procedural knowledge and procedural knowledge is exactly what a skill holds. Write the tag allowlists, the image policies and the table rule down once, in Markdown, in your repository. And if you write a version field, put it inside metadata.

FAQ

What happened to Agent Skills in October 2026?

Anthropic donated the Agent Skills open standard to the Agentic AI Foundation, which sits under the Linux Foundation. Anthropic handed over the Agent Skills name and logo, the GitHub organization and the agentskills.io domain. The two lead maintainers are Mahesh Murag and David Soria Parra, and the project now sits at Impact Stage on the AAIF Technical Committee's project list, alongside ten other AAIF projects such as Model Context Protocol, AGENTS.MD and OpenSandbox.

How many AI tools support Agent Skills?

The specification repository's client showcase lists 46 agent products that support the format, including ChatGPT and Codex, Claude Code, Cursor, GitHub Copilot, VS Code, Gemini CLI, Goose, OpenHands, Hermes Agent and OpenClaw. Anthropic's own announcement puts the adoption figure at more than 70 agent platforms, 1 million published skills and nearly 280 million installs as of October 22, 2026. The showcase is the verifiable list; the announcement numbers are the vendor's own.

What are the exact rules for a SKILL.md file?

The name field is required, must be 1 to 64 characters, may contain only lowercase letters, digits and hyphens, cannot start or end with a hyphen, cannot contain consecutive hyphens, and must match the parent directory name. The description field is required and may run up to 1024 characters. The optional compatibility field is capped at 500 characters. The optional license, metadata and allowed-tools fields have no length cap. No other top-level field is allowed.

Can I put a version field in my skill's frontmatter?

Not at the top level. The reference validator rejects any frontmatter field outside name, description, license, compatibility, metadata and allowed-tools, so a top-level version field fails with an unexpected-fields error. The fix is to nest it inside metadata, where the specification's own example puts it. We confirmed this by running both forms against the validator: the top-level form was rejected and the nested form was accepted.

What does Agent Skills do for a Markdown writer who publishes to LinkedIn and X?

It gives an agent a durable, version-controlled folder of instructions for converting Markdown into the rich text each platform actually accepts. The instructions are the same Markdown you already write, so they diff, review and version like everything else. A skill can encode the tag allowlists and image policies for Medium, X Articles and LinkedIn so the agent stops guessing at them on every draft.

Is Agent Skills safe to install from an unknown author?

The specification does not cover it. The format documentation contains no security guidance at all, and the words malicious, supply chain and prompt injection do not appear anywhere in the specification or the skill-creation guides. The governance document routes security issues to the core maintainers and mentions security implications as something a spec proposal must state, but that is a reporting path, not a review process for the skills themselves. Treat a skill folder with the same caution you would apply to any script you are about to run.
