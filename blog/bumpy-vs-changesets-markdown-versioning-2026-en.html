Bumpy vs Changesets 2026: Markdown-Driven Versioning Tested

Bumpy, a new Markdown-file-based versioning tool from the team behind Varlock, claims to fix over 120 open Changesets issues. We ran the workflow to see where it delivers — and where Changesets v3 still wins.

Every JavaScript monorepo eventually hits the same wall: how do we version and release all these packages without losing our minds? For years, the default answer has been Changesets — the file-based workflow where contributors drop a small Markdown file into .changeset/ declaring which packages to bump and why. It's simple, reviewable, and integrated into thousands of CI pipelines. But it's also accumulated a long list of open issues — over 120 by one count — around workspace protocols, prerelease state machines, and publishing flexibility.

Enter Bumpy. First unveiled in an April 2026 Show HN post by creator Theo Ephraim, and now shipping as @varlock/bumpy under an MIT license, Bumpy keeps the Markdown-file model that made Changesets popular and attacks the friction underneath it. The project describes itself as a successor, not just an alternative — and it's already being used to release Varlock alongside 25+ related libraries and plugins.

How Bumpy works

If you know Changesets, the Bumpy workflow will feel immediately familiar. Contributors write a small Markdown "bump file" into .bumpy/:

---
'@myorg/core': minor
'@myorg/utils': patch
---

Added user lang prefs to core config.
Fixed locale fallback logic in utils.

The frontmatter declares which packages get released and at what semver level. The body becomes the changelog entry. Because these are plain Markdown files stored in git, they show up in your PR diff for review, consolidate into a release PR via CI, and merge cleanly when that PR lands. Nothing about this surface changes from Changesets — and that's deliberate.

Where Bumpy diverges is everything beneath that surface. The headline features:

  • Workspace and catalog protocol support — workspace: and catalog: protocols work across npm, pnpm, Yarn, and Bun, without the platform-specific workarounds Changesets users have had to maintain
  • Per-package custom publish commands — publish VS Code extensions, Docker images, or JSR targets from the same release pipeline, not just npm packages
  • Configurable dependency propagation — a three-phase algorithm lets teams decide exactly how peer dependency bumps cascade through the package graph, rather than accepting Changesets' one-size-fits-all behavior
  • Branch-based prerelease channels — prerelease versions are derived at publish time and never committed to git, sidestepping the state-machine complexity that Changesets' own docs call "very hard to fix"
  • Lean CI — two commands, bumpy ci check and bumpy ci release, run in a standard GitHub Actions workflow with no GitHub App to install or separate action repo to trust

The AI agent angle

One Bumpy feature that has no Changesets equivalent: an agent skill that teaches LLMs how to inspect git changes, identify affected packages, and generate bump files via bumpy add. It installs through the Vercel Labs skills CLI, the GitHub CLI, or as a Claude Code plugin.

This matters because it points at where release management is heading. The Show HN thread was candid that Bumpy "was coded using AI, but carefully" — and the tool is designed to be operated by AI agents, not just humans. In a world where AI agents write code, review PRs, and triage issues, the release workflow is a natural next target. A Markdown-file-based versioning system is uniquely well-suited to this: the files are human-readable, diff-able, and LLM-friendly in a way that JSON config or database state never will be.

Should you migrate?

The honest answer in November 2026: it depends on which Changesets pain points you actually feel. Changesets v3 shipped in August 2026 and closed many of the long-standing issues Bumpy originally targeted. Bumpy's own differences doc now compares against v3 and credits it as "a substantial cleanup" — while pointing out remaining gaps around configurable propagation, catalogs, custom publish targets, and prerelease workflows.

Migration is low-friction if you do decide to try it. Running bunx bumpy init on an existing Changesets project migrates bump files and config automatically. But be aware of the gaps the community has flagged — Yarn 4.10 catalog detection being the most commonly cited — and weigh them against the v3 improvements before committing a large monorepo.

For new projects starting fresh, Bumpy is a credible default. The file-based model is proven (Changesets proved it), and Bumpy's workspace/catalog support plus lean CI story remove real friction. The MIT license and TypeScript implementation keep the risk profile low.

FAQ

What is Bumpy and how does it differ from Changesets?

Bumpy is an MIT-licensed, TypeScript-based version management and changelog tool for monorepos, created by the team behind Varlock and first announced in April 2026. It follows the same file-based workflow as Changesets but adds workspace and catalog protocol support across npm, pnpm, Yarn, and Bun, per-package custom publish commands, a configurable three-phase dependency propagation algorithm, and branch-based prerelease channels. It claims to address more than 120 open issues from Changesets.

Is Bumpy a drop-in replacement for Changesets?

Bumpy is designed as a successor rather than a drop-in replacement. Running bunx bumpy init on an existing Changesets project automatically migrates bump files and configuration. However, teams evaluating migration have flagged gaps such as Yarn 4.10 catalog detection. Additionally, Changesets v3 (released August 2026) closed many of the long-standing issues Bumpy originally targeted, so the calculus depends on which specific pain points matter most to your team.

What are bump files in Bumpy?

Bump files are small Markdown files that Bumpy contributors drop into the .bumpy/ directory. Each file declares which packages should be released, at what semver level (major, minor, or patch), along with a changelog description. Because they are plain Markdown files stored in git, they are fully reviewable in pull request diffs, can be edited collaboratively, and consolidate into a release PR via CI when that PR merges.

How does Bumpy handle prereleases?

Bumpy version 1.14 added branch-based prerelease channels where prerelease versions are derived at publish time and never committed to git. This directly targets a documented pain point in Changesets, whose own prerelease documentation describes its pre mode as very complicated with states that are very hard to fix. By deriving prerelease versions from the branch at publish time rather than committing them, Bumpy avoids the state-management problems that have frustrated Changesets users.
